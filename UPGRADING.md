# Upgrading

What may change for you from one release to the next, newest first. There is no migration step and no state stored outside your libraries: reinstall (see [User Guide section 5](USER_GUIDE.md#upgrading--version-compatibility)) and run `git-remote-seafile doctor`. Every entry says the same two things, what is stored and what is renamed, and then the behaviours that may surface on a workflow that already works. The full list of changes is in [CHANGELOG.md](CHANGELOG.md); running a mixed fleet of versions is covered in the [User Guide](USER_GUIDE.md#upgrading--version-compatibility).

**Upgrading to v0.9.19** Nothing about what is stored changes and no setting is renamed. Behaviours that may surface on existing workflows: a push whose pack the server refuses (HTTP 413, or a closed connection on a body of 8 MiB or more) is retried in smaller packs instead of failing, and after a 413 sets `seafile.gcmaxpackmib` in that repository's git config with a `Notice:`; a library that does not exist, or a token refused while listing libraries, fails at once instead of printing `retrying once`; `git seafile-snapshot` with nowhere to push prints a `Warning:` (so `--exit-warnings` returns 3) where it printed one quiet line, and a first run at a terminal asks about reproducible directories (an unattended run never asks); `doctor` prints a `Warning:` when the library keeps full history or none. New: `login`, `config`, `lfs-setup`, `doctor --create-library` and `--set-history`, and a grouped `--help` for the snapshot tool.

**Upgrading to v0.9.18** Nothing about what is stored changes and no setting is renamed. Behaviours that may surface on existing workflows: `--payload-gc` and `--payload-verify` stop, naming the entry, when the remote's `refs/` holds a file or directory the helper cannot list as a ref (they used to carry on without that branch, and `--payload-delete` could then delete its objects); a `gc-pending.json` that is not a JSON object stops `--payload-gc --payload-delete` until it is removed, which loses nothing and delays deletion by a full grace period; `--payload-verify` refuses when the temporary volume cannot hold the remote's packs (`--allow-low-disk` overrides); `doctor` prints a `Warning:` rather than `[ ok ]` when its conflict-copy walk reaches its limit.

**Upgrading to v0.9.17** Nothing about what is stored changes and no setting is renamed. Behaviours that may surface on existing workflows: `doctor <url>` exits 1 while a Seafile conflict copy exists anywhere under the repository path, naming each one; a `--payload-gc` run refuses, before fetching, when the temporary volume cannot hold the remote's packs (`--allow-low-disk` overrides); `--status` gains a `pushed` line (and `pushed` / `unpushed` in `--json`) and compares the sizes of git-stored files, which a vault written before this release does only after its tree next changes. New: `doctor <url> --upload-limit [--max-mib N]`.

**Upgrading to v0.9.16** Nothing about what is stored changes and no setting is renamed. Behaviours that may surface on existing workflows: a new snapshot vault pointed at a `--remote` that already holds a chain prints a `Note:` saying which chain it joins, and a `Warning:` (so `--exit-warnings` returns 3) when fewer than half of that snapshot's files exist in the source; `--default-excludes` keeps a recommended pattern for the run when the source's own git repository tracks a file it matches; a ref write is one attempt with a 20-second reply timeout, so a server that does not answer produces `the ref may or may not have been written` instead of a ten-minute wait; the automatic tail merge now merges the smallest packs that fit its budget instead of deferring on every push (and takes a smaller budget on a link it measured as slow); a restore on Windows restores around names Windows cannot hold and lists them; `--status --json` carries every key with `null` counts when nothing can be compared. New: `--payload-skip-changing`. The link rates a vault remembers are stored to four significant figures.

**Upgrading to v0.9.15** Nothing about what is stored changes and no setting is renamed. `git seafile-snapshot --status` and `git-remote-seafile repair` are new commands. Three behaviours may surface on existing workflows: a push of the other object format (SHA-1 into a SHA-256 remote or the reverse) is refused, naming both formats; `--status` refuses `--no-push` and `--dry-run`; and a snapshot vault's `info/attributes` gains `-working-tree-encoding` on its next run, so a source that uses that attribute stores the file's real bytes and records a change for it once. Lock tickets gain a per-install id (`~/.git-remote-seafile/install-id`); older tickets are still honoured.

**Upgrading to v0.9.14** Nothing about what is stored changes and no setting is renamed. The retention grace period now runs on the server's time (a machine clock jump between the mark and the delete used to delete early); the payload history-rewrite fence cannot be erased by a torn marker; the lock fails closed over an unreadable ticket; and a fresh vault whose default cut-off differs from the remote's recorded ratio is refused, naming `--payload-auto-ratio` to repeat. A restore refuses a destination volume with under 1 GiB free before the clone; `gc` and the tail merge print a `progress:` line during the long captured phases; and the package ships its `py.typed` marker. CI runs nine test legs instead of fifteen.

**Upgrading to v0.9.13** Nothing about what is stored changes and no setting is renamed. Two refusals are new and may surface on existing workflows: a push from a shallow clone is refused (run `git fetch --unshallow` first), and a ref name the server would store differently — not NFC-normalised, a double quote, or over 255 UTF-8 bytes — is refused instead of silently overwriting a twin branch. The lock is renewed during long pack builds and repacks, an upload whose lease is provably lost stops instead of finishing, a truncated-pack push removes what it posted, a fetch no longer wedges after an interrupted multi-pack download, and a damaged payload object no longer blocks every later snapshot. New flag: `--rebuild-index` re-reads every git-stored file (the git-side `--payload-rehash`). A scheduled `--json` job gains its document on Ctrl-C (`status: "failed"`), a wrapped `Error:` keeps its listed paths, and the push's own warnings now count for `--exit-warnings`.

**Upgrading to v0.9.12** Nothing about what is stored changes and no setting is renamed; the exit codes of a run are what they were (`--exit-warnings`, which adds `3`, is opt-in). Hashing, a payload restore and `--payload-verify` now print a `progress:` line once a minute, as an upload does. New: `--restore-drill`, `--json`, `--exit-warnings`.

**Upgrading to v0.9.11** Nothing about what is stored changes and no setting is renamed. Output that a script reading it would notice: notifications are in title case (`Warning:`, `Note:`, `Notice:`, `Hint:`, `Error:`; the snapshot tool's fatal error was `error:`, and 0.9.10's placement suggestion was `tip:`); byte counts are `KiB`/`MiB`/`GiB` (the snapshot tool printed `KB`/`MB`/`GB` for the same numbers, and the helper's `Uploading packfile` line and `gc`'s `saved ~N` changed with them; the `saved_kb` field of gc's JSON output keeps its name). `--default-excludes` now also leaves out any Python virtualenv it finds (a directory holding `pyvenv.cfg`), which the vault remembers as an ordinary exclude. A run that fails on a file still being written now uploads everything else and keeps its hashes; the file is named, and `--exclude` leaves it out.

**Upgrading to v0.9.10** Nothing changes for an existing vault, and nothing about what is stored changes. A new vault with a gigabyte or more of compressible 4–64 MiB files measures once on its first real run: four 16 MiB probe files are uploaded to the payload store and deleted (eight library-history entries), and the cut-off is remembered. `--dry-run` measures nothing. To choose a cut-off for an existing vault, run once with `--payload-auto-ratio measure` or `--payload-auto-ratio R`; files then move between git and payload once, and copies already in history stay there.

**Upgrading to v0.9.9** is the same as upgrading to v0.9.8, which was tagged but never released: `git seafile-snapshot` run from a subfolder of a repository now snapshots the whole repository (with a note), and an explicit `--source` naming a subfolder is refused; a vault that already remembers a subfolder keeps working. Nothing about what is stored changes.

**Upgrading to v0.9.8 from v0.9.7** changes nothing for a setup that works, except that `git seafile-snapshot` run from a subfolder of a repository now snapshots the whole repository (with a note), and an explicit `--source` naming a subfolder is refused; a vault that already remembers a subfolder keeps working. Nothing about what is stored changes.

**Upgrading to v0.9.7 from v0.9.6** changes nothing for a setup that works: upload retries obtain a fresh single-use upload link to prevent HTTP 400 errors, `seafile-doctor errors` displays all errors under the default `--days 0` filter, stale lock tickets from recycled local PIDs are fast-reclaimed via process start time verification, `repo.db` access is consolidated, and snapshot vaults pin `core.quotepath = false` to display UTF-8/Thai paths without octal escaping. Nothing about what is stored changes.

**Upgrading to v0.9.6 from v0.9.5** changes nothing for a setup that works: a push of a repository with very long (non-ASCII) paths on Windows no longer fails with "expected object ID, got garbage". Nothing about what is stored changes.

**Upgrading to v0.9.5 from v0.9.4** changes nothing for a setup that works: a server under a path (`https://host/seafile`) can now be named in `SEAFILE_SERVER`, the credentials file or the desktop client's account (section 7.1), and that account's URL is used when the remote names the same host and port. Nothing about what is stored changes.

**Upgrading to v0.9.4 from v0.9.3** changes two timings and nothing else: `gc` and the tail merge read the new pack back and compare its SHA-256 before deleting (one more download of that pack under the lock), and a snapshot lists its payload objects once more after the push. Neither changes what is stored.

**Upgrading to v0.9.3 from v0.9.2** changes behaviour in three places: on Windows every large payload file is hashed once more on the first run (the cache key now uses NTFS's change time, which catches a same-size in-place edit that put the modification time back); plain `unlock` refuses a ticket held by a live process on this machine (`--force` still breaks it); and `--payload-gc --payload-delete` re-reads the remote's refs while it deletes and stops if another machine pushed. Nothing else changes for a working setup.

**Upgrading to v0.9.2 from v0.9.1** changes behaviour in four places: a directory the snapshot tool cannot read stops the run and is named (it used to be silently left out; `--exclude` it on purpose); a snapshot that pushes to a `seafile://` remote also records the modification time of every git-stored file, and `--restore` puts the times back (`--no-record-mtimes` turns it off); `git push --force-with-lease` works; and `--payload-gc` stops, deleting nothing, if a branch's ref cannot be read or a push landed while it was deciding. No file format changed.

**Upgrading to v0.9.1 from v0.9.0** changes behaviour in four places: `gc` stops (deleting nothing) when a ref or refs directory cannot be read, so re-run it after a transient failure; a push lists the pack directory and re-reads the refs under the lock (two more requests); a nested git repository in a snapshot source is captured as its files (`--no-embedded-repos` keeps the old record); pack names must be lowercase. No file format changed.

**Upgrading to v0.8.8 from v0.8.7 or earlier changes four defaults you may notice:**

- `seafile.autogc` is now **on**: after a qualifying push the helper merges the small packs. `git config seafile.autogc false` restores the tip-only behaviour (§10.2).
- Subcommand **usage errors exit 2 on stderr** (they used to exit 1 on stdout); results and reports stay on stdout. Re-check any script that parsed the old stream (§14, *Output and Exit Codes*).
- `seafile.locksettle` and `seafile.gcmaxmib` are no longer settings; a value still in your git config is reported once and ignored. `seafile.gcmaxpackmib` now means the largest pack the helper writes, and the automatic budget is 2 x it.
- The snapshot tool now **refuses to stage a tree the vault's volume cannot hold** (`--allow-low-disk` overrides), and `--restore` without `--branch` uses the remote's only branch.
